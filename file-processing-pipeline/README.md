# Serverless File-Processing Pipeline

A fully event-driven, serverless pipeline built on AWS. Uploading a file to S3 automatically triggers processing — no manual invocation needed.

## Architecture

```
                 ┌─────────────────────┐
   User/App ───► │   S3: Upload Bucket │
                 └──────────┬──────────┘
                            │ ObjectCreated event
              ┌─────────────┴─────────────┐
              │                           │
     suffix: .jpg                 suffix: .pdf
              │                           │
              ▼                           ▼
   ┌─────────────────────┐   ┌─────────────────────┐
   │ Lambda:              │   │ Lambda:              │
   │ ImageResizeFunction  │   │ PdfParseFunction     │
   │ (sharp)              │   │ (pdf-parse)          │
   └──────────┬───────────┘   └──────────┬───────────┘
              │                          │
              ▼                          ▼
   ┌─────────────────────────────────────────────┐
   │        S3: Processed Bucket                  │
   │  /thumbnails/*.jpg   /extracted-text/*.txt   │
   └───────────────────────────────────────────────┘
              │                          │
              └────────────┬─────────────┘
                            ▼
                 ┌─────────────────────┐
                 │  DynamoDB:           │
                 │  FileMetadata table  │
                 └─────────────────────┘
```

- **Trigger:** S3 event notifications route uploads to the correct Lambda based on file suffix — no manual routing logic needed.
- **Image processing:** resizes uploaded images to a 300px-wide thumbnail using `sharp`.
- **PDF processing:** extracts text and page count using `pdf-parse`, saves the full text to S3 and a 500-character preview to DynamoDB (to stay under DynamoDB's 400KB item limit).
- **Metadata tracking:** every file — successful or failed — gets a record in DynamoDB with a unique `fileId`, status, timestamps, and source/destination keys.

## Tech stack

| Component | Choice |
|---|---|
| Runtime | Node.js 20.x |
| IaC / deploy tool | AWS SAM |
| Compute | AWS Lambda |
| Storage | Amazon S3 (2 buckets: uploads, processed) |
| Metadata store | Amazon DynamoDB |
| Image processing | `sharp` |
| PDF processing | `pdf-parse` |

## Prerequisites

- Node.js 20+
- AWS CLI v2, configured (`aws configure`)
- AWS SAM CLI
- Docker Desktop (with WSL2 backend on Windows) — required for `sam build --use-container`, which compiles native dependencies (`sharp`) against Amazon Linux rather than your local OS

## Build & deploy

```bash
# Install dependencies for each function
cd image-resize && npm install && cd ..
cd pdf-parse && npm install && cd ..

# Build inside a Lambda-matching container (important for sharp's native binaries)
sam build --use-container

# Deploy (first time)
sam deploy --guided

# Deploy (subsequent updates)
sam deploy
```

## Testing

Upload a file directly to the upload bucket and watch it get processed automatically:

```bash
# Image
aws s3 cp test-image.jpg s3://file-pipeline-uploads-<ACCOUNT_ID>/test-image.jpg --region ap-south-1

# PDF
aws s3 cp test.pdf s3://file-pipeline-uploads-<ACCOUNT_ID>/test.pdf --region ap-south-1
```

Check results:

```bash
# Thumbnails
aws s3 ls s3://file-pipeline-processed-<ACCOUNT_ID>/thumbnails/ --region ap-south-1

# Extracted text
aws s3 ls s3://file-pipeline-processed-<ACCOUNT_ID>/extracted-text/ --region ap-south-1

# Metadata
aws dynamodb scan --table-name FileMetadata --region ap-south-1
```

## Security notes

- Each Lambda function has its own auto-generated, least-privilege IAM role (via SAM's `S3ReadPolicy`, `S3CrudPolicy`, `DynamoDBCrudPolicy` policy templates) — scoped only to the specific bucket/table it needs.
- The CLI deploy user (`dev-sam-cli`) is scoped to a custom policy limited to this project's resources (CloudFormation, S3 buckets prefixed `file-pipeline-*`, this specific Lambda/DynamoDB resource set) rather than `AdministratorAccess`.
- A billing alert/budget is configured to catch unexpected costs early.

## Known design decisions

- **S3 notification wiring is manual, not auto-generated by SAM.** Two Lambda functions triggering off the same bucket causes a circular CloudFormation dependency if you use SAM's built-in `Events: S3` shorthand on both functions. This is solved by defining `AWS::Lambda::Permission` resources explicitly and configuring the bucket's `NotificationConfiguration` by hand, with `DependsOn` enforcing creation order.
- **DynamoDB stores only a text preview for PDFs**, not the full extracted text, to stay well under the 400KB per-item limit. Full text lives in S3.

## Cleanup

To avoid any ongoing costs, tear down all resources when done experimenting:

```bash
sam delete
```

This removes the CloudFormation stack and all resources it created (Lambda functions, S3 buckets, DynamoDB table). Note: S3 buckets must be empty before SAM can delete them — if `sam delete` fails on a non-empty bucket, empty it first with `aws s3 rm s3://<bucket-name> --recursive`.
